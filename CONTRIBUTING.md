# Contributing

Thanks for considering a contribution. These are personal projects, and outside
help can make them better—but a contribution also asks someone to review,
understand, and maintain a change. A little coordination goes a long way.

Individual repositories may have more specific guidance. When they do, that
guidance takes precedence over this file.

## Before you start

- **Found a bug?** Search the project’s issues first. If it hasn’t been
  reported, open an issue with clear reproduction steps, what you expected, and
  what happened instead.
- **Have a small fix?** Typo corrections, focused bug fixes, and similarly
  contained changes can usually go straight to a pull request.
- **Planning something substantial?** Please open an issue before investing a
  lot of time. We can compare goals, constraints, and approaches before either
  of us disappears down a rabbit hole.
- **Found a security problem?** Don’t report it publicly. Follow the
  [security policy][security].
- **Need help using the project?** Start with the [support policy][support].

An issue is a conversation, not a reservation. Opening one doesn’t guarantee
that I’ll accept or implement the proposed change.

## Make the change

Keep the work focused enough that someone unfamiliar with your branch can
reason about it. Follow the patterns already used by the project, and avoid
bundling unrelated cleanup into the same pull request.

Before submitting, please:

1. Run the project’s relevant tests, linters, and build steps.
2. Add or update tests when behavior changes.
3. Update documentation for anything people need to learn or do differently.
4. Consider keyboard, screen reader, zoom, reduced-motion, contrast, and other
   accessibility needs relevant to the change. My broader commitments are in
   the [accessibility statement][accessibility].
5. Confirm that you have the right to contribute the code and content, including
   third-party dependencies, images, and other assets.

If you can’t complete one of these steps, say so in the pull request. Context is
more useful than pretending a gap isn’t there.

## AI-assisted contributions

AI-assisted contributions are welcome when you:

- Disclose the use of AI in the pull request
- Review, understand, and test everything you submit
- Verify licenses, attribution, and the provenance of generated material
- Take responsibility for the contribution just as you would for work written
  without AI assistance

“The tool wrote it” isn’t a useful explanation for a bug, an inaccessible
interaction, or code you can’t maintain. Please don’t submit unreviewed output.

## Licensing your contribution

Unless a repository says otherwise, by submitting a contribution you agree that
it may be distributed under that repository’s existing terms:

- Source code and code examples under its software license—MIT by default
- Original prose, documentation, images, and other non-code content under
  [CC BY-NC-SA 4.0][content-license]

Third-party material and files with their own license notices remain under their
stated terms.

## What to expect

I maintain these projects in my own time. Some are active; some are experiments,
historical artifacts, or tools I revisit only when a need resurfaces. I can’t
promise a response time, and I may decline a technically sound contribution
because it doesn’t fit the project’s direction or maintenance budget.

If I ask for changes, I’ll try to explain why. If I close a proposal, that
isn’t a judgment on the value of the idea—or the person who offered it. It may
simply be the wrong fit for this particular project.

By participating, you agree to follow the
[Code of Conduct][conduct].
